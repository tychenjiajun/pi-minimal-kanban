Backlog #4. A 100-task board must not cost 100+ lines per call.

Acceptance criteria:
- [ ] `kanban_list` accepts `limit` (default 50, max 200) and `offset` (default 0); ordering is stable (status order, then task id).
- [ ] When rows are omitted, the text states exactly how many were omitted and how to see them, per `docs/product/design-v0.2.md`.
- [ ] `summary: true` returns per-status counts and claimed counts without task rows.
- [ ] `structuredContent` gains `total`, `offset`, `limit`, `truncated` (additive; existing fields unchanged).
- [ ] The workflow block is still printed (agents rely on it); it must not grow with board size.
- [ ] Tests cover limit/offset/truncation/summary on a board with > 50 tasks, and assert the text reports omitted rows.

Out of scope: session-level caching of the workflow block.

## Adversarial review (T-0004) — fix-then-merge

Verified against design §2/§3 by driving the real tool: 137-task board, all pages (0/50/100/137/200), `/kanban` columns, a drifted board, a 12-status workflow.

1. **P1 — `src/schemas.ts:181` + `src/index.ts:420`: `limit` is capped at 200; design §3 says 1-500, and a real agent asking for 500 is *rejected*, not clamped.** `Value.Check(ListParams, {limit: 500}) === false`, so TypeBox validation fails before `execute` and the `Math.min(…, 200)` clamp is dead code for tool calls. **Recommendation: implement 500** — design §3 is the binding surface (T-0002 exists precisely so the three code tasks cannot drift from it), 500 is a superset of the task's "max 200", and the value is opt-in so there is no context cost. Also change `README` ("max `200`") and the schema description. If PM prefers 200, change design §3 and README instead — but do not leave the two documents contradicting each other; today they disagree and this task's own comment records the deviation without resolving it.

2. **P1 — `src/render.ts:150-157`: drifted tasks in `/kanban` use a second, legacy row format.** Actual output: `    T-0001  legacy task  [working]` — no `rev`, no aligned `@handle`, `[status]` in brackets. Design §2: "One row shape is used by `kanban_list` and by the columns of `/kanban`" and "A drifted task keeps its raw status id and gains ` ⚠` after it; the marker sits inside `statusWidth`, so the title column does not shift". Consequence: `rev` disappears for exactly the tasks T-0007 promised it for, and `/kanban` and `kanban_list` describe the same task differently (`working ⚠ … rev 1` vs `[working]`). Fix: render this block with `renderTaskRows(drilled, { indent: 4, showStatus: false })`; `statusCell` already appends the drift marker (and `drifted` tasks would then also show the claim age when relevant).

3. **P1 — `src/command.ts:212-231`: `/kanban mine <handle>` and `/kanban status <id>` bypass the §2 row too.** Actual: `  T-0001  working  ok task @a 0s` — no `rev`, no column alignment, `@handle` glued to the title. Design §4 says the age appears "using the row format in Section 2: … and in `/kanban mine <handle>`". Fix: `renderTaskRows(tasks, { indent: 2 })` (with `showStatus: false` for `mine`, `true` for `status`). This is the cheapest way to make the "rev is visible everywhere" promise true.

4. **P2 — `src/index.ts:411`: `summary: true` returns `limit: 0`, `offset: 0`, `returned: 0`.** `limit`'s declared minimum is 1, so an agent that echoes a read-back `limit` into the next call gets a validation error; design §3 says summary is "counts only, no paging", so the honest shape is to omit the paging fields. (`total` is correct here.)

5. **P2 — `src/schemas.ts:230-233`: the `truncated` alias comment is false.** It says "kept for callers that already use the name", but `truncated` did not exist before this release, so there are no such callers. Either drop the alias (design only asks for `hasMore`) or fix the comment to say it is a redundant convenience field.

**AC status:** met. `limit`/`offset` accepted with defaults, filtering before paging, stable status-then-id order with drifted last, `offset >= total` not an error; exact §3 sentences verified byte-for-byte — header `  showing 51-100 of 137 (offset 50, limit 50)`, footer `  ... 37 more tasks (of 137). Next: offset 100, or narrow the filters.`, `  No tasks at offset 137; 137 match. Reset with offset 0.`, and `No matching tasks.` + hint; `summary: true` matches §3 (label width `longest+2`, 4-column right-aligned counts, `terminal` note, drifted line) and applies filters; workflow block identical for 5- and 137-task boards; text and `structuredContent` agree on every page (137/50/50/37, `hasMore` true only when `offset + returned < total`). Row layout matches the §2 example exactly for the three sample rows (76 columns, `@coder-1 3d`, right-aligned `rev`) — title truncation excepted (reported on T-0007 as P1 #4).
