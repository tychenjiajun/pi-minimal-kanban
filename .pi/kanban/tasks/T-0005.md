Backlog #5. One malformed task file currently blanks the whole board (readTasks throws).

Acceptance criteria:
- [ ] A task file that cannot be parsed or validated is excluded from the board and reported as a problem with its path and the parse error.
- [ ] `kanban_list` returns the readable tasks plus `fileErrors: [{path, message}]` in `structuredContent`, and a warning block in text.
- [ ] `/kanban` renders all readable tasks and lists unreadable files in the warning block.
- [ ] `/kanban validate` reports each unreadable file as a problem with code `unreadable_task`.
- [ ] A task read directly by id (`kanban_list task: T-0002`) still fails clearly when that specific file is broken.
- [ ] Tests: one valid + one malformed task file; board still lists the valid one; validate reports the bad one.

Note: keep `docs/adr/0007` (drifted tasks stay visible) consistent; extend it or add an ADR if the read contract changes.

## Adversarial review (T-0005) — fix-then-merge

The core contract holds; one path still hides a broken file from the agent-facing surface.

1. **P1 — `src/index.ts:370-386` (+ `src/render.ts:461`): an all-unreadable board is treated as empty, so the briefing replaces the warning.**
   Reproduction: board with a valid workflow and one file `T-0001.md` containing `junk\n`. `kanban_list` (no params) returns the pristine onboarding briefing with `total: 0` — `text` contains neither `T-0001.md` nor `could not be read`; only `structuredContent.fileErrors` mentions it. A fresh agent is told "empty board, start here" while the board is corrupt. This is the "one bad file blanks the board" failure re-entering through the empty-board shortcut, on the surface agents actually use.
   Fix: `emptyBoard = board.tasks.length === 0 && board.fileErrors.length === 0 && !statusFilter && !assigneeFilter`, and prepend `renderFileErrors(board.fileErrors, { mode: "both", cwd: ctx.cwd })` to the briefing text (same root cause as the T-0003 finding — fix it in one place).

2. **P1 — `src/command.ts:212-231`: `/kanban status <id>` and `/kanban mine <handle>` drop unreadable files with no warning at all.** Verified: `status working` prints only the readable row. The AC only covers the full board, but these filtered views are how a human/agent decides "no such task"; a broken file simply disappears. Fix: append `renderFileErrors(board.fileErrors, { mode: "summary", cwd })` to `renderTaskList`.

3. **P2 — `src/render.ts:74-80`: every warning line repeats the path.** `FileError.message` already begins with the absolute path, so the block reads `⚠ tasks/T-0002.md  /abs/…/tasks/T-0002.md does not start with YAML frontmatter.` Fix: strip a leading `error.path` from `error.message` when rendering, or store a bare message in `fileErrors`.

4. **P2 — `src/store.ts:825`: `unreadable_task` swallows every non-`id_mismatch` code**, including `no_such_task` (file deleted between `listTaskIds` and the read), so the problem can name a file that no longer exists. Acceptable, but consider carrying the `KanbanError` code in `ValidationProblem` so the report is honest about which failure it saw.

**AC status:** met. `readTasks`/`readBoard` return `{tasks, fileErrors}` and a single bad file never throws out of a board read (`store.ts:222-238`); parse/validation failures are excluded and reported with `path` + `message`; `kanban_list` prints the warning block (`text` contains "could not be read" and the file name) and repeats the list in `structuredContent.fileErrors`; `/kanban` renders the readable columns plus the `⚠ Unreadable task files` block; `/kanban validate` reports `unreadable_task` with `path`, `severity: "problem"`, and flips `ok: false`; a direct `kanban_list {task: "T-0002"}` fails with `Error [invalid_task]` and the parse message; ADR 0007 documents the read contract.

**Checked specifically for a mutation targeting a broken file** (the "silently dropped" trap): `kanban_move` on the unreadable task fails with `Error [invalid_task]` and leaves the bytes untouched; `/kanban release T-0001 --yes` on it fails the same way and writes nothing. No silent write-over, no silent skip. Good.

**Test gap (P2):** `resilience.test.ts` and the new `acceptance.test.ts` only assert `toContain("could not be read")` with a *valid* file present; nothing asserts the all-unreadable case or the filtered views, which is how finding 1 and 2 passed.
