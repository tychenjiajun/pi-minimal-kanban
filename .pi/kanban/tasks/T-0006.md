Backlog #1. A claim left by a departed agent must be visible and releasable.

Acceptance criteria:
- [ ] Claim age (time since the claim started, derived from history) is shown wherever an assignee is shown: `kanban_list` rows, `/kanban`, `/kanban mine`, and `/kanban <task>`.
- [ ] `/kanban validate` reports code `stale_claim` when a claim is older than a threshold (default 24h, overridable by the second argument or `PI_KANBAN_STALE_CLAIM_MS`), and keeps reporting `active_unassigned` only for active tasks with no assignee.
- [ ] The `wrong_owner` error includes the claim age and names the exact call that releases it (`kanban_assign` with `force: true, assignee: null`, or `/kanban release <id>`).
- [ ] `/kanban release <id>` releases a claim, requires explicit confirmation (interactive) or `--yes` (non-interactive), records a forced unassign in history, and refuses when the task has no claim or is terminal.
- [ ] A stale claim is a warning, not an error: `/kanban validate` still exits "valid" wording separately from problems? (Keep the existing report shape; mark stale claims under problems but document them as warnings.)
- [ ] Tests: claim age rendered; stale_claim at threshold; release works, records history, and is refused without a claim; wrong_owner text names the release call.
- [ ] `README.md` and `docs/adr/0004` document the release path.

Out of scope: leases or heartbeats (ADR 0004 forbids them).

## Adversarial review (T-0006) — fix-then-merge

The age formatter, the warning-vs-problem split, and the release mechanics are right. The confirmation is not binding, two refusal paths print a false drift marker or no age, and one class of blocking assignment is invisible.

1. **P1 — `src/command.ts:285` + `:318`: `/kanban release --yes` re-reads nothing and passes no `expectedRev`, so it can release a claim that was taken over after the confirmation was rendered.** Verified repro: `@coder-1` owns T-0001; the confirmation is rendered (`owner @coder-1`, `rev 2`); `@beta` force-claims the task; `/kanban release T-0001 --yes` then prints `was @beta` and clears **@beta's** claim — the human authorised releasing a different owner's claim, and the `rev` the block printed was decorative. Fix: pass `expectedRev: task.rev` from the confirmation read (the `stale` envelope already tells the operator to re-read), or do the read inside the same lock as the write. That turns a silent takeover-loss into an actionable error and matches the expectedRev discipline the tools already advertise.

2. **P1 — `src/store.ts:345-348`: `claimedFor` returns `""` outside an active status, so `wrong_owner`/`already_assigned` print no age.** Verified: `Error [wrong_owner]: Task T-0001 is claimed by "gone"; "other" cannot move it, because that would take the claim.` No age, even though the assignment is 10 months old. Design §4: "Every `wrong_owner` message states the claim age"; ADR 0004 (shipped by this task) says every refusal "names both the claim age and that call". Fix: fall back to the `updated`-based age when `!task.active` — the same `formatAge` applies (design §0.1 explicitly says the formatter is unchanged when exclusivity widens). Or soften design §4 + ADR 0004; today the docs and the code disagree.

3. **P1 — `src/store.ts:784`: a stale *assignment* in a non-active status is never reported, but it still blocks every move into an active status.** Verified: task assigned to `gone` in status `new`, history 10 months old → `validate` returns `problems: []` (ok: true), and yet `kanban_move {to: "working", agent: "other"}` fails `wrong_owner` because `claimBound = target.active` (`store.ts:491`). Because the briefing and README also say "an assignee outside an active status is not a claim", an agent reading them concludes the task is free — it is not. Fix: add a distinct warning (e.g. `stale_assignment`) for a non-active assignee older than the threshold, or at minimum show its age in the refusal (finding 2).

4. **P1 — `src/command.ts:295`: the "no claim" refusal prints a false drift marker.** Verified: `T-0001 has no claim to release.` / `  status  new ⚠` for a status the workflow declares (also `  status  done ⚠` for a terminal one). ⚠ is ADR 0007's drifted-status marker, so this says the board is broken when it is not; design §5's block is `  status  new`. Fix: `task.drifted ? `${known} ⚠` : known` (the code already does this correctly for the `now` line at `:320`).

5. **P1 — `src/command.ts:324-325`: the success block's columns are not aligned.** Actual `  now  unassigned  working  rev 3` vs design §5 `  now  unassigned     reviewing  rev 12`. Cosmetic, but it is a literal fenced block an agent may parse. Fix: pad `unassigned` to the `was`-line width (`@handle` + age).

6. **P2 — `src/command.ts:266`: the stale warning prints under `Warnings:`.** Design §4's block puts it under `Tasks:` (header `Board is valid (1 warning).` is correct). Cosmetic.

7. **P2 — `--stale` error codes.** `--stale ""` (`command.ts:196`) throws `invalid_task` and the command appends the hint paragraph; `--stale x` throws `invalid_argument` with no hint. Design §4 wants one hard error: `Invalid --stale "x"; use 30m, 12h, 7d, or 0.` Use `invalid_argument` for both.

8. **P2 — `src/store.ts:588`: `forced: true` is omitted when the operator is also the assignee.** Design §5 shows `{action: "unassign", by: "<operator>", assignee: "coder-1", forced: true}` unconditionally, and docs/task-file.md says a release "carries `forced: true`". Either always set it or document the exception.

9. **P2 — docs drift.** `README.md:52` still shows the pre-v0.2 column row (`@coder-1  rev 2`, no claim age; the shipped row is `@coder-1  0s  rev 2`), and `README.md:15` still says the command "only renders" while the same file documents the `release` exception. ADR 0004's "names both the claim age" is inaccurate per finding 2.

10. **P2 — task text:** AC 2 ("keeps reporting `active_unassigned` only for active tasks with no assignee") contradicts design §4 ("The `active_unassigned` problem is deleted"); the code correctly follows design. Update the AC so the tester does not re-litigate it.

**Verified met:** age grammar matches the §0.1 table at every boundary (0s, 45s, 59s, 1m, 59m, 1h, 23h, 1d, 13d, 2w; negative → 0s) and `claimStart` follows the specified last-assign/force-assign-then-`updated` rule; thresholds render as `24h`/`30m`/`7d`; `stale_claim` is `severity: "warning"`, is strictly `> threshold`, and keeps `report.ok === true`; `--stale 0` and `PI_KANBAN_STALE_MS` (alias `…_CLAIM_MS`) disable/replace; `No leases`/`never expires` wording is in the briefing, help, and ADR 0004 — no expiry logic anywhere. `/kanban release` without `--yes` writes nothing (bytes unchanged), `--yes` clears the assignee, bumps `rev`, and records `{unassign, by: "human", forced: true}`; the no-claim and terminal refusals write nothing; `--as`/`PI_KANBAN_HANDLE` are validated by the same handle regex; `/kanban help` is exactly the ten §6 lines; ages appear in rows, columns, `mine`, and as `(claimed 3d)` in the task view.
