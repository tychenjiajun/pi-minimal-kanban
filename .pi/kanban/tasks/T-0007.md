## Adversarial review (T-0007) — fix-then-merge

Reviewed `src/` read-only against `docs/product/design-v0.2.md` and this task's ACs. Gates re-run: `npx vitest run` 144/145 pass (the one failure is the unrelated `package.json` 0.2.0 release criterion), `npx tsc --noEmit` clean. Findings ordered by severity.

1. **P0 — `src/fs.ts:123-129` and `:136-139`: the board lock can be held by two processes; `release()` can delete a foreign lock.**
   - Steal TOCTOU: a waiter that decided the owner was stale calls the blind `removeLock(lockDir)` (line 125) with no re-read of `owner.json`. If the old owner released and a third process acquired in between, the waiter deletes *that* process's live lock and then mkdirs its own — two owners, interleaved read-modify-write. Concrete damage inside `store.ts`: two `reserveTaskId` calls read the same counter and both write `next + 1`, and two `writeTask` calls `atomicWrite` the same path (one task vanishes).
   - `release()` only skips when `current.token !== owner.token`; when `owner.json` is missing/unreadable `current` is `undefined`, so our own release falls through to `removeLock()` and deletes whoever holds it now. That is exactly the state a stealer leaves behind.
   - Untested: `src/test/concurrency.test.ts` covers in-process chaining, one foreign-owner timeout, and one two-child claim race — never a stale steal, and never `release` against a replaced lock.
   - Fix: steal by atomic rename — `renameSync(lockDir, lockDir + `.steal.` + token)`, then `rmSync` only if the renamed `owner.json` still carries the token you observed (otherwise rename it back and retry). In `release`, remove only when `current?.token === owner.token`; treat unreadable `owner.json` as "not ours" and let the 120 s age reclaim handle it. Add a test with two processes stealing one stale lock asserting exactly one winner.

2. **P1 — `src/store.ts:864-871`: `counter_low` is computed from readable tasks only.** `highest` comes from `tasks`; if the highest-numbered file is the unreadable one (the T-0005 case) the low counter is not reported, and when every file is unreadable `highest = 0` silently disables the check — the exact hand-edited-board failure this AC exists to catch. Fix: derive `highest` from `listTaskIds(location)` (filenames), not the parsed tasks.

3. **P1 — `src/render.ts:419` (with `:19`): handle truncation is off by two and can lengthen the cell.** `task.assignee.length > 13` truncates any 14-character handle; design §2 truncates the *cell* only when `@handle` exceeds 16 characters. `@abcdefghijklmn` (valid, 15-wide cell) prints as `@abcdefghijklm...`, i.e. 17 characters, wider than what it replaced. `MAX_META_WIDTH = 17` also contradicts the design's cap of 16. Fix: truncate only when ``@${handle}`.length > 16`.

4. **P1 — `src/render.ts:400` + `:44`: title truncation keeps the space before the ellipsis.** Actual row: `T-0003  reviewing  Make an abandoned claim visible ...  @reviewer 5h  rev 11`; design §2 is `visible...` ("truncated to `titleWidth - 3` (trailing spaces removed) + `...`"). Fix: `text.slice(0, limit - 3).replace(/ +$/, "") + "..."` in `truncate`.

5. **P2 — `src/index.ts:70-79`: a failure can name the wrong board.** `boardLocationFor` retries with `cwd` when `project` does not resolve, so `kanban_move {project: "/nope"}` returns `root`/`dir` of the cwd board, which was never involved. Fix: only fall back when `project` is absent.

6. **P2 — two codes for one argument error.** `--stale ""` throws `invalid_task` (`src/command.ts:196`) while `--stale x` throws `invalid_argument` (`src/store.ts:637`), and the command path appends a hint for the former only. Use `invalid_argument` for both.
