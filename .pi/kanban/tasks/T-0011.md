Reviewer-2 round findings on T-0008. The rename-then-verify steal is right, but four holes remain. Details are in the reviewer-2 comment on T-0008.

- [ ] **F1 (P1) atomic entry.** `acquire` must not create an empty `lockDir` and then write `owner.json` into it; that empty-directory window is what lets a restore silently replace a fresh lock. Build `<lockDir>.entry.<token>/owner.json` first and `rename` the non-empty entry dir onto `lockDir`; a non-empty rename onto an existing directory fails, so entry becomes all-or-nothing. The restore path in `stealLock` must never overwrite a directory it did not move.
- [ ] **F2 (P1) reap orphan tombstones.** A tombstone left by a crash (or by a deliberate leave) currently blocks every write forever with a misleading "remove <dir>/.lock". Reap tombstones whose `owner.json` is absent, or whose pid is dead on this host, or whose mtime exceeds the grace; name the tombstone path in the timeout error.
- [ ] **F3 (P2) `release` symmetrically.** Use rename-verify-delete instead of read-then-`rm -r`.
- [ ] **F4 (P1, test) make the concurrency test discriminate.** Add a deterministic seam (an injectable hook or delay between the staleness read and the delete) so the pre-fix blind-delete code fails the test; keep the current 8-process test as a smoke test and correct its inaccurate comment. Drop the "fails pre-fix" claim where it is not true.
- [ ] **F5 (P3).** Fix or remove the overstated test-claim note in the task comment.
- [ ] New tests for the F1 and F2 branches.
- [ ] `docs/task-file.md` "Concurrency" and ADR 0004 describe the final mechanism, including tombstone reaping and the entry directory.
- [ ] `npx vitest run` and `npx tsc --noEmit` clean; write a comment demonstrating that the F4 seam test fails on the pre-fix logic and passes on the new one.

Implemented T-0011 (F1/F2/F3/F4/F5).

**F1 — atomic entry.** `acquire` builds `<lock>.entry.<token>/owner.json` and `rename`s the **non-empty** entry dir onto `.lock`; ENOTEMPTY/EEXIST/ENOTDIR/EISDIR means someone else holds it. There is no empty lock directory any more, so a restore can never land on a half-built lock. The restore is also guarded: `restoreTombstone` renames back **only if the path is still absent** (`existsSync` check first, because POSIX `rename` onto an existing empty dir replaces it); otherwise the tombstone is left for the reaper.

**F2 — reaping.** `reapStrays` runs on every retry: deletes `.entry.*` older than the grace, every `.lock*.trash.*`, and any `.steal.*` tombstone with no `owner.json`, a dead pid on this host, or an mtime past the 5 s grace. A tombstone with a live, recent owner is kept (it may be about to put the lock back). The timeout error now names the blocking tombstone(s) instead of `.lock`. `release()` also deletes *its own* tombstone when a recovery had moved the lock aside — a live-pid tombstone is otherwise unreapable and stalls every writer for the whole grace.

**F3 — release is symmetric.** `release` = `disposeAside(lock, owner.token)`: rename aside, delete only if the moved dir still carries our token, rename back otherwise. All deletes go through `discard()` = rename to `.lock*.trash.<rand>` then `rm -r`, so a delete can never race a writer (`ENOTEMPTY`) and two deleters cannot collide.

**F4 — deterministic seam.** `LockOptions.beforeSteal(attempt)` runs between the staleness read and the delete; `stealLock`/`disposeAside` accept `StealHooks {beforeVerify, beforeRestore}`. Nothing in production sets them.

New tests (`src/test/concurrency.test.ts`, 8 new, 16 in the file):
- "does not delete a lock that changed hands between the staleness read and the delete" (P1 seam: a live token is written between read and delete; asserts the live lock survives)
- "refuses to restore a tombstone onto a directory it did not move" (`beforeRestore` creates an empty dir at the path; restore must refuse, tombstone stays)
- "never restores a tombstone onto a lock directory someone else created"
- "reaps tombstones a crashed recovery left behind" (ownerless + dead-pid tombstone; lock acquired anyway)
- "keeps a tombstone whose owner may still put it back, and names it on timeout"
- "takes its own tombstone with it when a recovery moved the lock aside"
- "never puts an empty lock directory in place", "releases only its own token, never a directory it did not move"

**Seam evidence (pre-fix vs new).** Temporarily replacing `disposeAside`'s verify with a blind delete (the round-1 logic):
- `npx vitest run src/test/concurrency.test.ts` → `Tests 7 failed | 9 passed (16)`; the seam test fails with `AssertionError: expected 'gone' to be 'live'` (the live owner's `owner.json` was deleted).
- Temporarily making `restoreTombstone` rename unconditionally (old restore) → "refuses to restore a tombstone onto a directory it did not move" fails (`expected true to be false`).
- Temporarily making `reapStrays` a no-op → "reaps tombstones a crashed recovery left behind" fails (times out).
- New code: `Tests 17 passed (17)`, and 10 consecutive full runs `Tests 1 failed | 183 passed (184)` — only the pre-existing `package.json` 0.2.0 criterion (T-0010 scope). `npx tsc --noEmit` clean.

**F5.** The round-1 note "the token/`release` unit tests fail deterministically" was wrong for the `release` test: the old code also returned early on a token mismatch and only deleted when `owner.json` was missing. Corrected here: against the reconstructed pre-fix code the *seam*, *restore*, *reap* and *no-owner grace* tests fail; the plain `release`-token test does not.

Docs: `docs/task-file.md` "Concurrency" and ADR 0004 "The board lock" now describe the entry directory, the verified restore, tombstone reaping and rename-then-remove deletes.

## Round-3 review: board lock — PASS (no P0/P1)

Verified: `npx vitest run src/test/concurrency.test.ts` → **17 passed** (17 tests in the file; the round-2 note says 16), `npx tsc --noEmit` → clean. Read-only on `src/`.

### Round-2 findings
- **F1 atomic entry — closed.** `acquire` builds `<lock>.entry.<token>/` with `owner.json` written, then `renameSync(entryDir, lockDir)`. POSIX rename onto a non-empty dir fails, so no empty-lock window exists. ENOTEMPTY/EEXIST/ENOTDIR/EISDIR are all treated as "someone else owns it". `restoreTombstone` guards with `existsSync(lockDir)` before renaming back — the check-then-rename race is **benign**: on Linux `rename(dir, non-empty dir)` = ENOTEMPTY and `rename(file, dir)` = EISDIR; only an *empty* dir is silently replaced, so the worst case is a lost restore into a stray empty dir, which is not a lock (holds no `owner.json`) and is reaped after the 5 s grace. Production entries are never empty, so a re-entrant third process cannot be a lock whose `owner.json` is somebody else's — the token is written before the rename and `readOwner(lockDir).token === owner.token` re-verifies after.
- **F2 orphan tombstones — closed.** `reapStrays` runs every retry; reaps `.entry.*` older than grace, every `.lock*.trash.*`, and `.steal.*` with no `owner.json`, dead pid on this host, or age > 5 s. Live+fresh tombstones are kept. Timeout error names the actual tombstone (confirmed: `... remove /tmp/.../.lock.steal.foreign if you know the owner crashed`). No unbounded growth path found — entries, trash, and tombstones all have an age/predicate reaper.
- **F3 release symmetry — closed.** `release` = `disposeAside(lockDir, owner.token)` + reaping only tombstones carrying `owner.token`. A foreign tombstone is untouched (probed: fresh pid-1 tombstone survives a full acquire/release cycle).
- **F4 test discrimination — closed.** `LockOptions.beforeSteal` (between staleness read and delete) and `StealHooks{beforeVerify,beforeRestore}` exist; the seam tests are deterministic and the round-2 pre-fix evidence (`7 failed | 9 passed` on blind delete, restore/reap tests failing when reverted) is credible.

### Seams (item 5)
`beforeSteal`/`StealHooks` are not reachable from the tool params: `store.ts` calls `withBoardLock(path, fn)` with **no options at all** (5 call sites, all 1-arg), and `schemas.ts` has no lock/timeout/hook input. `beforeSteal` is `await`ed only when defined; `hooks?.beforeVerify?.()` etc. are no-ops when absent. Behavior is unchanged when absent.

### Docs (item 6)
`docs/task-file.md` "Concurrency" and ADR 0004 "The board lock" match the code: entry dir, rename-verify-delete, `existsSync` restore guard, tombstone reaping with the same three predicates, rename-then-remove deletes. No lease/heartbeat language; ADR 0004 still explicitly rejects leases and states "nothing expires on a timer" for claims (the 2 min lock threshold is correctly framed as a lock-only steal).

### Remaining, non-blocking
- **P2 (docs):** `docs/task-file.md` says a tombstone is reaped "when it is older than the five-second grace" — the code uses `lockDirAgeMs(tombstone) > NO_OWNER_GRACE_MS` (mtime), so it is *idle* age, not creation age. Same in ADR 0004. Accurate but could say "mtime".
- **P2 (cosmetic):** `restoreTombstone`'s `existsSync` + `renameSync` sits inside a `try` whose `catch` swallows *all* errors, including ENOTEMPTY/EISDIR; that is the intended "lost the race" path, but the comment "Lost the race" would be clearer if it also noted an empty-dir replacement is impossible only because the entry is never empty.
- **P2 (test):** `restoreTombstone`'s empty-dir case is only covered via the `beforeRestore` seam creating an empty dir; no test covers a *third* entrant renaming a complete entry in between the `existsSync` and the `rename` (unreachable deterministically today, so acceptable).
- **P2 (test):** round-2 note says "8 new, 16 in the file"; the file has **17**.

Verdict: **PASS**. No P0/P1. F1–F4 genuinely closed.
