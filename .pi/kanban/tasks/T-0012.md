Backlog #9 (P2). In scope for v0.3.0. Vocabulary: `GLOSSARY.md` (Task, Claim, Forced assignment, Handle, History).

## Context
A Forced assignment currently records `forced: true` and nothing else (`src/store.ts` `assignTask` and `moveTask` push `{ at, action: "force-assign", by, assignee, forced: true }`). A later reader cannot tell "the owner crashed" from "the owner was preempted". History is already documented as self-reported (`GLOSSARY.md`), so a recorded reason buys legibility, not trust.

## Acceptance criteria (from `docs/product/backlog.md` #9)
- [ ] `kanban_assign` and `kanban_move` accept an optional `reason` when `force` is true.
- [ ] History entries for Forced assignments render the reason in `/kanban <task-id>`.
- [ ] A Forced assignment without a reason is accepted but flagged in `validate` as unannotated.

## Implementation notes
- `src/schemas.ts`: add `Reason` as `Type.Optional(Type.String({ maxLength: 200 }))` and add it to `AssignParams`, `MoveParams`, and `HistoryEntry`. Add the same `reason: Type.Optional(Type.String())` to the history entries in `TaskDetail`'s schema.
- `src/types.ts`: `HistoryEntry.reason?: string`.
- `src/store.ts`: add `reason` to `AssignInput` and `MoveInput`; trim it and record it only on `force-assign` / forced `unassign` entries. A `reason` passed without `force` is ignored (do not error — a hint is fine but not required); document that choice in the test name.
- `src/store.ts` `parseHistoryEntries` (the history reader): read `reason` when it is a non-empty string. Files without it keep round-tripping byte-identically.
- `src/store.ts` `validateBoard`: new problem code `unannotated_forced`, **severity `warning`** (not `problem` — an unannotated takeover must not make the board invalid). One warning per Task that has any `force-assign` or forced `unassign` entry with no `reason`. Message must name the Task and the date of the entry.
- `src/render.ts` `renderTask`: render `(forced: <reason>)` on a `force-assign` line that has a reason, keep ` (forced)` when it has none. Stay inside the 76-column budget; wrap/truncate the reason rather than overflowing.
- `src/command.ts`: `/kanban validate` renders the new warning through the existing `renderValidationReport` severity path; no new subcommand.
- `src/index.ts`: `kanban_assign` and `kanban_move` `promptGuidelines` gain one sentence: pass `reason` with `force` so the takeover is auditable.

## Tests to add
In `src/test/claims.test.ts` (or a new `src/test/reasons.test.ts`): a forced assign with a reason writes it to the file and `renderTask` prints it; a forced assign without a reason still succeeds and `validateBoard` reports `unannotated_forced` with `severity: "warning"` and `ok: true`; a task file written before this change (no `reason` key) still parses and re-serializes unchanged.

## Docs
- `README.md`: the `/kanban validate` paragraph gains `unannotated_forced`; the `kanban_assign`/`kanban_move` rows mention `reason`.
- `docs/workflow.md`: one line under validation on takeovers.
- `CHANGELOG.md` 0.3.0 section (release task writes it; leave a line in your PR/commit note).
- `docs/product/backlog.md`: tick item #9's three boxes only (prose untouched).

Do not bump `package.json` version. Do not add a runtime dependency.

- §1.3: `reason` requires `force`; argument errors precede the lock. - §1.2 move: `force+reason` on a non-takeover puts the reason on `move`, not the trailing `unassign`.
