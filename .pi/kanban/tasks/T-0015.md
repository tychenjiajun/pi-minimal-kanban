Backlog #12b (P2). In scope for v0.3.0. Sibling of "Complete task ids and handles in /kanban arguments"; land after it so the help text can describe the real completion behavior. Vocabulary: `GLOSSARY.md` (Board, Project, Task, Claim, Terminal status, Assignee, Handle).

## Context
`USAGE` in `src/command.ts` already states the Claim rule ("Moving a task into an active (◆) status claims it for your handle; only that handle can move or release it without force"), the Terminal-status rule ("A terminal status releases the claim"), and the Handle convention ("Handles are self-asserted names like coder-1; the board does not check them"). **Those three sentences are done — do not rewrite them.** The audit's claim that `/kanban help` "states no rules" is out of date (`docs/product/v0.3-scope.md` records this).

What `USAGE` does not say, and now must: (a) where completions look for the Board, and (b) what happens when there is no Board.

## Acceptance criteria
- [ ] `/kanban help` states the Claim rule, the Terminal-status rule, and the Handle convention (already true — a test must now pin it so a later edit cannot silently drop it).
- [ ] `/kanban help` states that argument completions use the session's Board, that they list Task IDs and Handles, and that without a Board only subcommands are completed.
- [ ] `/kanban help` remains at most 14 lines and every line is at most 76 characters.
- [ ] A test asserts the help text contains one literal phrase for each of the four rules (substring assertions, not snapshots of the whole block).

## Implementation notes

  `  session board; with no board it completes subcommands only.`
  Do not delete the `Start with kanban_list` line.
- Add a short "where the board is" line only if it fits and is needed: the README already covers `PI_KANBAN_DIR`; `USAGE` should stay a help card, not a manual.
