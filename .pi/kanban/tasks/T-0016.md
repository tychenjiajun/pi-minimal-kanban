Backlog #13 (P2), the remaining half. In scope for v0.3.0. Vocabulary: `GLOSSARY.md` (Board, Board lock, Task, Task ID, Drifted task); rule source `docs/adr/0005`.

## Context
`validateBoard` in `src/store.ts` already reports `id_mismatch` (a Task file whose frontmatter `id` disagrees with its filename — raised by `toTask`) and `counter_low` (`counter.json` not greater than the highest existing Task ID). Those two checkboxes are shipped. What does not exist is a repair path: the only fix is hand-editing YAML, after a `counter.json` merge conflict that `docs/adr/0005` and `README.md` say will happen.

## Acceptance criteria (from `docs/product/backlog.md` #13)
- [ ] `/kanban validate` reports a Task whose `id` frontmatter does not match its filename. *(already shipped — pin it with a test, do not change it)*
- [ ] `validate` reports a `counter.json` value that is not greater than the highest existing Task ID. *(already shipped — pin it)*
- [ ] `/kanban repair-ids --dry-run` lists the renumbering it would perform.
- [ ] `/kanban repair-ids --yes` performs that renumbering.

## Scope boundary — state it in the docs, do not implement it
Renumbering references to a Task ID **inside descriptions and comments is explicitly NOT required and must not be attempted**. `repair-ids` rewrites exactly two things: the task file's name and its frontmatter `id`. A `T-0007` mentioned in prose stays as written. Say so in the `--dry-run` footer, in `README.md`, and in the CHANGELOG line.

## Semantics to implement (decide nothing else)
- Source of truth for a file's identity is its **filename**. A file whose frontmatter `id` differs is *repaired to the filename*, never the reverse — the filename is what `listTaskIds`/`readTask`/every tool use.
- A frontmatter `id` that is *missing* or not a string is not an `id_mismatch` (it is `invalid_task`); `repair-ids` reports it and skips it, it does not invent an id.
- Two files cannot resolve to the same filename (`listTaskIds` dedupes by digit string), so no conflict resolution is needed; assert it rather than handling it.
- After repair, `counter.json` is rewritten only when `next` is not greater than the highest existing Task ID, set to `highest + 1`. Never lower the counter (`docs/adr/0005`: an ID once issued is never reused).
- Writes happen **under the board lock** (`withBoardLock`), one task at a time, frontmatter rewritten via the existing `serializeTaskFile` + `parseDocument` path so comments and unknown keys survive. Do not re-serialize with a plain `Document` if the raw frontmatter is available.
- `--dry-run` and `--yes` are mutually exclusive and the command refuses with neither... unless the existing `/kanban release` convention is followed. Match `/kanban release`: **write nothing and print the plan** unless `--yes` is passed, and accept `--dry-run` as an explicit synonym for that. Both must be honest about whether anything was written.

## Safety rules, as implemented
- **Filename is identity.** The plan is enumerated from `listTaskIds` only; a differing frontmatter `id` produces a rename *to the declared id* and nothing else. The frontmatter is not rewritten at all — after the rename `id:` and filename agree, so the file stays byte-identical (there is a test for that, which is also the "no `rev`/`updated`/history rewrite" guarantee).
- **Never apply a printed plan.** `repairIds` takes no plan; it re-plans inside the lock (test: a plan computed before a hand edit is not what runs).
- **`--dry-run` takes no lock, writes nothing.** Tested by a full `.pi/kanban` byte snapshot + `.lock` absence.
- **Two-pass rename.** `T-xxxx.md → .repair.<token>.<filenameId>.md → target`, one `randomBytes(6)` token per run. Swap and chain both tested.
- **Counter never lowered.** Only raised (`highest + 1` over filenames ∪ rename targets) when `from <= highest`; otherwise the file is not written at all (tested byte-identical).
- **No prose, `rev`, `updated`, history, or comment rewriting.** Tested with a body and a comment that mention the old id.
- **`--dry-run --yes`** is refused before anything else happens. `--as` goes through the existing `resolveOperator` (`invalid_handle`).

## Two spec readings I had to resolve (both recorded here, no behaviour is ambiguous)
1. **§5.4 "A rename target that already exists" vs §5.5 "so two swaps cannot collide".** Read literally, a target that exists is always a refusal — but in a swap (`T-0002` declares `T-0005`, `T-0005` declares `T-0002`) **both** targets exist, and §7 check 11 requires the swap to apply. I implemented the rule as: a target that exists **and is not itself a source in this plan** is a refusal; a target that is another rename's source is fine (pass 1 moves it aside). That is the only reading under which checks 7 and 11 are both true, which is the release-criteria test §0 of my brief sets.
2. **`REPAIR_TEMP` naming.** §5.5 writes the staging name as `.repair.<token>.md` (so a whole run shares one name and pass 1 could not stage two files). I kept one token per run, as specified, and made the staged name `.repair.<token>.<filenameId>.md` so it is unique per file; it still never matches `/^T-(\d{4,})\.md$/`, and §5.1's leftover message is unchanged and detected by `/^\.repair\..*\.md$/`.

## Two additions the spec implies but does not literally define
- A frontmatter `id` that is a string but **not** a canonical task id (e.g. `id: coder-1`) is skipped with `invalid id "<value>" in frontmatter` rather than renamed: renaming would produce a file no tool reads, which is worse than a refusal. A broken/absent frontmatter gets `not a readable task file` so every skipped row still carries a message.
- A counter-only plan prints `Repaired 1 task id.` per §5.3, and in plan form prints `0 files would be renamed.` so the "N files" sentence never renders as `0 file would be renamed.`

## For the reviewer
- **Do not "simplify" the refusal order.** `repairRefusal(plan)` runs before the empty-plan early return, so a board with a duplicate id and nothing else to do still refuses instead of saying "Nothing to repair".
- `--yes` re-checks the refusal after re-planning under the lock; the dry run and the bare invocation also refuse (same text), so a refusal can never be worked around by omitting the flag.
- The plan prints `Docs and comments that mention <first renamed filenameId> are not rewritten` — the spec's footer names a single id, so a multi-rename plan names the first (lowest filename id). Worth a look if you want it pluralised.
- `repairIds` calls `assertHandle` **before** taking the lock, matching `assignTask`.
- `counter` is read with `readCounter`, whose default for an absent file is `1`; §5.2 prints `next 1` there rather than inventing a file.
