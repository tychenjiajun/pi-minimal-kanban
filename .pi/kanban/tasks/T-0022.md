## Reproduction
`docs/product/design-v0.3.md` §1.2's table, row 4:

| `kanban_move {force:true}`, takes another handle's task | `force-assign`, `move`, `assign` | `force-assign` |

But `store.ts` `moveTask` appends `force-assign` then `move`, and only appends
`assign` when `target.active && !assignee` — after the forced takeover
`assignee` is already the caller, so no `assign` is written.

Actual history for a takeover move (scratch board, `planning -> building`,
coworker holds it, `force:true`):
```
create -> move -> assign:own-1 -> force-assign:own-2[reason] -> move
```
i.e. `force-assign, move` — the table's trailing `assign` is absent.

For a takeover into a terminal status the actual entries are
`force-assign, move, unassign` (table row 4 says `assign`).

## Expected
Either the table is corrected to `force-assign, move` (+ `unassign` when the
target is terminal), or the implementation appends the redundant `assign`.

## Actual
Documentation and implementation disagree on the exact history sequence. The
reason placement (the thing the release is about) is correct: it is on the
`force-assign` entry in both cases, as the table's third column promises.

## Severity
post-release (documentation mismatch only; no behaviour, locking, or reason
placement is affected). It matters because §1.2 is presented as a precise
per-call table an implementer or test author is told to trust.

## Evidence
Takeover move on a scratch board; `readBoard` history sequence listed above.
This is the only §1.2 row I could not reproduce exactly.
