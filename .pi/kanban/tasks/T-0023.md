**Blocks the v0.3.0 tag.** Found by `release-v03` while bumping the version.

## Symptom
`npx vitest run` fails exactly one test after `package.json` becomes `0.3.0`:

```
src/test/acceptance.test.ts:463
✕ release criteria: packaged version > is bumped to 0.2.0 in package.json
  expected '0.3.0' to be '0.2.0'
```

## Root cause
`src/test/acceptance.test.ts` (the `release criteria: packaged version` block, ~line 458) hardcodes the
version of the release it was written for:

```ts
it("is bumped to 0.2.0 in package.json", () => {
  // v0.2-scope.md: "Version bumped to 0.2.0 in package.json."
  ...
  expect(packageJson.version).toBe("0.2.0");
});
```

That is a snapshot of v0.2.0's own release, not a rule. It must fail on every future release, so the
suite is red for reasons unrelated to code, and the next person either edits the test in a hurry or
learns to ignore a red suite. Both are worse than the bug.

## Required fix (do not just change the literal)
Make the test assert the *invariant*, not one release's value:
- The test title must be release-agnostic (e.g. "matches the newest CHANGELOG release").
- Assert `package.json` `version` equals the first `## <semver>` heading in `CHANGELOG.md`, so
  package and changelog cannot drift — that is the release criterion that actually matters.
- Keep a second, cheap assertion that the version is valid semver (`/^\d+\.\d+\.\d+$/`), so the test
  still says something if the CHANGELOG heading is malformed.
- Add a test that fails when the two disagree (temporarily point the reader at a fixture string, or
  export the comparison as a small helper and feed it `("0.3.0", "## 0.2.0")`). Do not mutate the real
  `package.json`/`CHANGELOG.md` in a test.
- Reference the release criteria the check now serves (`docs/product/v0.3-scope.md`), and drop the stale
  `v0.2-scope.md` comment. If a comment must cite a doc, write the rule, not the file path of one
  release's scope.

## Acceptance criteria
- [ ] `npx vitest run` is fully green on the current tree (which is at 0.3.0) with no change to
      `package.json` or `CHANGELOG.md`.
- [ ] `npx tsc --noEmit` clean.
- [ ] The `release criteria: packaged version` test no longer contains the string `0.2.0`;
      `rg -n "0\.2\.0" src/test/` returns nothing.
- [ ] The new test fails if `package.json` and the newest CHANGELOG heading disagree (prove it once,
      locally, then restore).
- [ ] Test count is 264 or more; no existing test is deleted or weakened.

## Out of scope
Do not touch the version, the CHANGELOG, or any other test. This is a test-design fix, nothing else.

<!-- kanban:comment at=2026-10-31T17:45:13.201Z by=dev-c -->
Fixed the test design so the release gate asserts the invariant, not one release's literal.

**Files changed (only these two)**
- `src/test/helpers.ts`: added `SEMVER` (`/^\d+\.\d+\.\d+$/`), `newestChangelogVersion(changelog)` (semver of the first `## <semver>` heading), and `versionsAgree(packageVersion, changelog)` (compares the packaged version to that heading).
- `src/test/acceptance.test.ts`: replaced the hardcoded `"is bumped to 0.2.0 ..."` test with two:
  - `release criteria: packaged version > matches the newest CHANGELOG release` — reads `package.json` and `CHANGELOG.md`, asserts a newest semver heading exists, asserts the package version is well-formed semver, and asserts `versionsAgree(packageJson.version, changelog)`.
  - `... > flags a packaged version that drifts from the newest CHANGELOG release` — feeds `versionsAgree` disagreeing/agreeing fixtures (`"1.0.0"` vs `"## 0.9.9"`, then `"## 1.0.0"`); real files are never mutated.

**Mechanism**: pass/fail now depends only on whether `package.json`'s `version` equals the semver on the first `## <semver>` heading in `CHANGELOG.md`. No literal version is pinned; the fixture test proves the comparison returns false on drift and true on agreement. The stale `v0.2-scope.md` inline comment is gone and the block cites the rule plus `docs/product/v0.3-scope.md`.

**How I proved it fails on disagreement**: with `package.json` left at `0.3.0`, I temporarily pointed the `CHANGELOG.md` read in the invariant test at the fixture `"# Changelog\n\n## 0.9.9 - scratch"` (acceptance-test-only edit, backed up to `/tmp` and restored in an `EXIT` trap). `npx vitest run src/test/acceptance.test.ts -t "matches the newest CHANGELOG release"` went red: `AssertionError: expected true to be false` at the `versionsAgree(...)` line. After the trap restored the file, `diff` against the backup was identical and no `scratch` marker remained; re-ran the full suite green.

**Verification**
- `npx tsc --noEmit` → clean.
- `npx vitest run` → 16 files, **265 passed** (before: 264 tests, 1 failed / 263 passed).
- `rg -n "0\.2\.0" src/test/acceptance.test.ts` → none.

**Flag for review**: the global `rg -n "0\.2\.0" src/test/` still returns three *unrelated* occurrences that are not version assertions — `claims.test.ts:385` (a `title: ... under 0.2.0` fixture) and `reasons.test.ts:257,263` (a pre-0.3.0 history-shape comment and a `title: ... from 0.2.0` fixture). Per the ground rules I did not touch other tests. If the acceptance criterion is meant literally, those coincidental fixture strings need a separate decision; the `release criteria: packaged version` test itself is now free of `0.2.0`.
