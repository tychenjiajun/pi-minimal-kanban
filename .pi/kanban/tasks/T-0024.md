**Process gap, not a product bug.** Found by the manager after the v0.3.0 tag, while dogfooding the board.

## What happened
This org shipped v0.3.0 using `pi-minimal-kanban` as its own board, as the project intends. Every board
write in that session went through the extension **pi loaded at session start** — the v0.2.0 code — because
`pi` registers packages under `~/.pi/agent/settings.json` (`"../../projects/pi-extenstions/pi-minimal-kanban"`)
when the session boots.

Symptoms, all consistent with v0.2.0 semantics rather than a v0.3.0 defect:
- `kanban_move`/`kanban_assign` calls that passed `reason` wrote **no** `reason` key (v0.2.0's schema had no
  such parameter, so the harness dropped it silently).
- `kanban_assign` to a third handle succeeded without `force` (v0.2.0 behaviour; v0.3.0 refuses).
- `/kanban validate` on this board reports 10 historic `unannotated_forced` warnings — correct, because
  those entries really were written without a reason.
- Direct calls into `src/store.ts` on a scratch board behave exactly as designed: the reason is stored on
  the `force-assign` entry, survives the round trip, and clears the warning. The shipped code is right.

## Why the gate missed it
`docs/product/v0.3.0-qa.md` proves the release criteria by running the **source** (tests and direct module
calls). No step loaded the built extension into a fresh pi session. So nothing in the gate could notice
that the session's *live* tools were a stale snapshot, and a whole release was managed with the previous
version's tool semantics.

## What to add
- [ ] A release-gate step: start a fresh session (or `/reload`) with the published/updated package path,
      then drive `kanban_create` → `kanban_assign {force, reason}` → `/kanban validate` and diff the
      observed behaviour against the tagged release. Record it in the QA doc.
- [ ] `README.md` gains one line: changes to this extension take effect for a session only after `/reload`
      or a restart, because tools are registered at session start.
- [ ] `docs/product/v0.3.0-qa.md` gains a short "What this gate does not cover" note naming in-session
      tool loading.

## Notes
- Do not rewrite the 10 historic board entries to silence the warnings: that is exactly the §1.7
  backward-compatibility behaviour, and rewriting history is forbidden (ADR 0004, `GLOSSARY.md`).
- No source change is expected. If this turns into code, it is a diagnostic (e.g. `/kanban about` printing
  the loaded package version) — propose it as its own task first.
